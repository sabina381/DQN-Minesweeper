# Minesweeper

## 1. 서론

이 프로젝트는 강화학습 동아리 팀프로젝트(2인, 각자 개인 파트를 진행하고 결과만 비교하는 방식)로 처음 시작됐다. 지뢰찾기는 규칙은 단순하지만 "주변 지뢰 개수"라는 제한된 시그널만으로 숨겨진 지뢰(risk)를 피해 안전한 칸을 골라야 하는, 알고리즘적으로 정답을 계산하기는 어려운 문제다. 이 문제를 DQN(Deep Q-Network)으로 직접 구현해 에이전트가 스스로 풀도록 학습시키는 것이 목표였다.

동아리 프로젝트가 끝난 뒤, 당시 코드에 남아있던 명확한 버그와 구조적 한계(하이퍼파라미터가 전역 변수로 흩어져 있던 점, guess 판정 로직이 가장자리 칸에서 오작동하던 점 등)를 스스로 인지하고 있었고, 이를 실제로 고쳐서 더 신뢰할 수 있는 실험 결과를 얻어보고자 이 프로젝트를 개인적으로 리팩토링·디벨롭했다.

## 2. 방법

**데이터**: 별도의 외부 데이터셋 없이, 직접 구현한 지뢰찾기 환경(`environment.py`)에서 에이전트가 플레이하며 생성하는 학습/검증/테스트 로그를 데이터로 사용했다. 각 실험은 학습 곡선 이미지, 게임 렌더링 이미지, 지표 로그(pickle)를 자동으로 저장한다.

**접근 방법**: 게임 보드를 (9×9, 11채널) one-hot으로 인코딩한 state를 입력으로, batch normalization을 적용한 CNN 기반 Q-network(`net.py`)가 각 칸의 Q값을 예측한다. ε-greedy 탐험과 replay memory를 사용하는 DQN 에이전트(`dqn_agent.py`)로 학습하며, 학습 중 `latest`/`best` 두 모델을 분리 관리해 성능이 일정 기준(`MODEL_CRITERIA`) 이상 정체되면 직전 `best` 모델로 롤백하는 안정화 로직을 두었다. 학습·평가는 `Trainer`/`Tester`(`Trainer` 상속) 클래스로 오케스트레이션하고, `Log` 클래스가 train/valid/test 지표를 모드별로 관리한다.

**사용 기술**: Python, PyTorch(`torch`, `torch.nn`, `torch.optim`), `easydict`(설정 관리), `numpy`/`pandas`/`matplotlib`/`seaborn`(로그 처리·시각화), R(`DQN_Minesweeper_DS.Rmd` — 결과 통계 검정).

## 3. 결과

최종적으로 비교·분석에 사용한 것은 A1(19만 episode), A2(30만 episode), B(20만 episode, 첫 클릭도 지뢰일 수 있는 `FIRST_MINE=True` 대신 `FIRST_MINE=False`로 학습) 세 모델이다. 지뢰 9개 환경에서 각 모델의 `best` 모델로 10,000판씩 실측한 결과는 다음과 같다.

- **A2(30만 episode)가 세 모델 중 가장 우수**: `first_mine=True` 기준 승률 72.1%, 평균 RPC 0.682로 A1(67.7%, 0.638)·B(58.4%, 0.567)를 모두 앞섰다.
- R 통계 검정 결과, **A2는 A1보다 승률·reward·RPC 모두에서 통계적으로 유의하게 우수했고(유의수준 5%), 분산도 더 작아 더 안정적인 성능을 보였다.** 지뢰 개수가 늘어날수록 A2와 A1의 성능 차이가 더 커졌다.
- **A1은 B보다도 모든 지표에서 유의하게 우수했다** — 즉 첫 클릭이 지뢰일 위험을 감수하며 학습한 모델이, 그 위험이 제거된 환경에서 학습한 모델보다 오히려 더 견고했다.
- 두 번째 턴 조기 패배율에서도 **A2가 세 모델 중 가장 낮아**, 지뢰 위치에 대한 확률적 판단 능력이 가장 뛰어난 것으로 나타났다.
- 이 결과를 근거로 **A2를 최종 모델로 선정**했다. 검정 방법론과 세부 수치·그래프는 `Minesweeper_통계분석_report.md`에 정리했다.

## 4. 논의 및 의의

가장 주목할 만한 발견은 First-Click Safety(첫 클릭이 지뢰가 아니도록 보장하는 기능) 유무에 따른 A1-B 비교 결과다. 상식적으로는 첫 클릭의 위험을 제거해준 환경(B)이 학습에 더 유리할 것으로 예상할 수 있지만, 실제로는 그 반대였다. 이는 첫 클릭에서도 지뢰를 만날 수 있는 환경이 에이전트에게 더 풍부하고 다양한 학습 신호를 제공했을 가능성을 시사한다.

또한 `best`/`latest` 모델 이원화와 롤백 로직 도입 전에는 학습 episode가 15만을 넘어가면서 성능이 급락하는 경우가 잦았지만, 도입 후에는 30만 episode까지 학습해도 성능이 꾸준히 우상향했다. 이는 강화학습처럼 학습이 불안정해지기 쉬운 태스크에서, 단순히 마지막 모델을 쓰는 것보다 검증 기반으로 최적 시점의 모델을 별도 보관하는 것이 실질적인 성능 향상으로 이어질 수 있음을 보여준다.

## 5. 한계점

- `dqn_modelA_400k` 폴더는 A2를 30만 episode 이후 실수로 `FIRST_MINE`을 False로 바꿔 이어 학습한 부산물로, 최종 비교에서 제외했다. 실험 결과물 네이밍·관리 체계가 이런 실수를 방지할 만큼 견고하지 못했다.
- `utils.py`의 `original`/`normalization` state encoding 경로는 구현만 되어 있고 실제 실험에서는 한 번도 사용되지 않았다.
- 9×9, 지뢰 7~12개 범위에서만 검증했고, 더 큰 보드 크기나 다른 지뢰 밀도에 대한 일반화 성능은 확인하지 않았다.


## 6. 향후 계획

- 학습 종료 시점에 실제 도달한 episode 수를 `config.txt`에 추가로 기록해, 설정과 실제 실행 결과가 어긋나는 문제를 재발 방지한다.
- `original`/`normalization` state encoding을 실제로 비교 실험한다.
- 9×9보다 큰 보드, 다른 지뢰 밀도에서도 A2/A1/B의 우열 관계가 유지되는지 검증한다.
- 실험 폴더 네이밍을 실행 시각이나 핵심 설정값 기반으로 자동 생성하도록 바꿔, `dqn_modelA_400k`와 같은 관리 실수를 구조적으로 줄인다.

## 7. 회고

동아리 프로젝트 당시(`norule` 파트) 스스로 인지하고 있던 문제들 — `self.` 참조 누락으로 인한 NameError, `display()` import 누락, guess 판정 로직이 가장자리 칸에서 오작동하던 버그, 행동 횟수 제한값이 느슨하게 설정돼 있던 점 — 을 이번 리팩토링에서 실제로 대부분 고쳤다. 더불어 하이퍼파라미터를 `config.py` 한 곳으로 모으고, 학습/평가 로직을 `Trainer`/`Tester`/`Log` 클래스로 분리했으며, `best`/`latest` 모델 이원화로 학습 안정성을 크게 개선했다.

가장 크게 배운 점은 두 가지다. 첫째, 코드를 고치는 것만으로 끝나는 게 아니라 "고쳤다"는 근거를 실측 데이터로 남겨야 한다는 것 — 이전 프로젝트에는 없었던, 지뢰 개수·`FIRST_MINE` 조합별 반복 테스트와 R 통계 검정을 도입함으로써 결과에 대한 신뢰도를 크게 높일 수 있었다. 둘째, 실험을 반복하다 보면 `config.txt`와 실제 학습 로그가 어긋나거나(`dqn_modelB_200k`), 실수로 다른 설정을 이어 학습한 부산물(`dqn_modelA_400k`)이 남는 등 예상치 못한 관리 실수가 생긴다는 것 — 이런 실수를 나중에라도 코드와 로그를 대조해 정확히 짚어낼 수 있어야, 잘못된 결론을 그대로 포트폴리오에 남기지 않을 수 있다는 것을 이번 문서화 과정에서 체감했다.
